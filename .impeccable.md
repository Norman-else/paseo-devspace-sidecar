## Design Context

### Users
The project owner is a developer reviewing changes made by a VPS coding agent in a Mac DevSpace worktree. The job is to inspect the current task's actual file changes without identifying infrastructure or choosing from unrelated workspaces.

### Brand Personality
Use Paseo's existing visual language: restrained, precise, and familiar. Let the host theme provide chrome colors and typography; use the supplied Claude Code reference for neutral code surfaces and change fills. This is an editor sidebar, not a standalone dashboard.

### Aesthetic Direction
The owner's Claude Code screenshot is the review reference: one continuous document containing every file's diff, with a compact flat file index on its right. Use understated file headers, collapsible code sections, old/new line gutters, syntax highlighting, green/red change backgrounds, and reviewed markers. Paseo supplies the surrounding chrome and theme. Avoid directory trees, workspace cards, implementation identifiers, and navigation to a separate page for each file.

### Design Principles
- Resolve the active task automatically; missing context gets a concise explanation rather than a global picker.
- Keep all file diffs in one continuous review surface; a flat right-hand index scrolls to a file in that same document.
- Only show the composer entry for a session that actually uses DevSpace.
- Show the branch and changes first; paths and infrastructure are secondary.
- Match the host language and theme. Wrap long code automatically at the available width without horizontal scrolling; keep original line numbers on the first visual line.
- Use Paseo's configured code font on desktop and browser, with a readable 14px minimum and matching line height. Use the neutral reference code palette in dark mode and readable pastel changes in light mode. Keep the changed-line backgrounds and left color strips distinct from the surrounding code surface.
- Present PR context as flat editor chrome above the diffs, without card framing, outer margins, or a separate background. Lead with the linked PR number and repository, using consistent 13px text, with branch direction on the right. Remove decorative PR and branch icons; keep only the external-link indicator. Follow with the title and compact icon-and-text statuses. Only the primary PR state uses a filled badge; long check lists stay expandable.
- Use one context header: PR details when a PR exists, otherwise the branch. Put the shared scope tabs, grouped change counts, and actions in a separate thin toolbar immediately above the diff, never inside a PR footer. Avoid duplicate branch titles and refresh buttons. Loading and unavailable PR states must remain distinct from a confirmed missing PR.

- Below 560px panel width, use a deliberate compact layout instead of wrapping desktop rows: left-align branch direction on its own line; keep scope tabs with search/index actions, then counts with collapse/refresh. Preserve all actions and use 44px toolbar touch targets.

- Keep the current file title pinned inside the diff viewport, below the review toolbar. Incoming file titles push the previous title away in both scroll directions. Preserve fold/review actions and keep pinning independent of recycled list rows.

- Keep review tools progressively disclosed: use a dedicated Comments tab for discussions and the PR check status for bounded CI details, one options dialog for review filters/checkpoints, and a selection-anchored floating feedback toolbar. Do not combine open search and PR details on narrow screens.
- Distinguish submitted PR code from the live worktree and label feedback with its actual source version. Attach comments only to a matching PR head and line side; outdated comments must stay separate.
- Keep code visible with compact inline discussion markers, expandable replies, and touch-sized actions. Use the file index for navigation instead of a redundant bottom navigation bar.

- Keep review decisions informational. Use a full Comments tab for discussion browsing, and offer file badges, inline markers, and previous/next comment navigation directly in Changes. Comment navigation must not require opening Comments first. Preserve the diff scroll position across tab changes.
- Make authors recognizable with avatars, public names, and GitHub handles. Give every reply its own identity; use login/initial fallbacks without adding extra anonymous iconography.

- Separate each reply with a full-width inset divider and generous vertical padding. Thread actions such as Request change and Show in diff must look like buttons, with visible borders, contrasting fills, hover/pressed feedback, and at least 44px height. Keep external GitHub navigation visibly link-styled.

- Select code with a draggable green + handle in its own non-selectable gutter. Anchor feedback actions beside the visible selection, never in a bottom bar that changes viewport height. Keep line numbers and diff markers out of copied text; support edge auto-scroll and hide the floating toolbar when its selection leaves the viewport.

- Use actual unmodified-line counts as clickable fold labels. Keep the fold control above the expanded source so it can be collapsed in place; cache context for reopening. The green + selection handle and its icon descendants must use an explicit plus-shaped cursor rather than a pointer.

- Name the filter menu File filters and explain each choice in place. Use Review baseline rather than review point; show its comparison scope and save time, explain disabled baseline filtering, and distinguish the first Save action from Update.

- Fold labels use at least 14px text and 16px icons, growing with the configured code size. Show their underline only while hovered; give the adjacent context hint a readable secondary code font. Keep virtual row heights aligned with the larger typography.
